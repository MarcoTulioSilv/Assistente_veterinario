# Ajustes de reunião — registrado em 2026-11-03

Lista de pedidos trazida pelo João (Dev 2) depois de uma reunião de alinhamento.
Cruzada com o estado do repositório na data do registro (branch `develop`,
commit `409ec43`) e com decisões tomadas junto com o João antes de qualquer
código ser alterado.

## Produtos (estoque)

- **Unidades de medida por categoria.** Ex.: vacina tem ml, dose, frasco e
  ampola. Hoje `unit` aceita qualquer um dos 12 valores pra qualquer
  categoria (`apps/ms-inventory/src/schemas/product.schema.ts`).
  **Classificação:** (a) só front/schema de validação — Dev 2.
  **Status:** pendente, vai ser feito em `feature/ms2-product-unit-validation`.

- **Preço por ml para medicamentos.** Não existe hoje um campo equivalente a
  `dosesPerUnit` (que resolve o caso análogo pra vacina) pra medicamento
  dosado por ml.
  **Classificação:** (b) precisa de campo novo no Prisma — Marco.
  **Status:** pendente, registrado em `Documentação/pedidos-para-marco.md`.

## Tela de animais

- **Remover "nome desenho".** Esclarecido com o João: não existe um campo de
  texto separado — é o label do campo de upload de resenha/desenho
  (`sketchUrl`), hoje rotulado "Resenha/desenho". A decisão foi **manter o
  campo** e só tirar a palavra "desenho" do texto do label, deixando
  "Resenha".
  **Classificação:** (a) só front, cosmético.
  **Status:** pendente, vai ser feito em `feature/pwa-animal-label-resenha`.

## Tela de atendimentos > cadastro de orçamento

- **Filtro de animais por propriedade.** Já em desenvolvimento (não
  commitado ainda na data deste registro) — select de propriedade filtra os
  animais exibidos.
- **Seleção de mais de um animal por orçamento.** Já em desenvolvimento,
  mesma tela. O contrato (`animalIds: UUID[]`, ficha/receita por animal) já
  existe desde a PR #34 do Marco (reunião de 20/10/2026).
- **Localização com mapa.** Já em desenvolvimento — reaproveita o
  `LocationPicker` (Leaflet) já usado na tela de Propriedades.
- **Valor por km do perfil do veterinário, preenchido automaticamente no
  orçamento, editável ali.** O campo e o contrato já existem
  (`TenantProfile.displacementRateCents`, PR #34). Faltava só a tela
  pré-preencher o form com esse valor ao criar um orçamento novo.
- **Remover "procedimento" dos itens; deixar apenas um campo de descrição.**
  Já feito desde a PR #34 (backend): `items` só aceita produto do estoque;
  o que era "procedimento" virou `procedureDescription` (texto livre) +
  `laborCents`.
- **Cálculo automático de km integrado a mapas.** Já havia uma
  implementação via Google (Routes API, `GoogleRouteAdapter`, PR #36) —
  **mas o Google Maps está bloqueado para uso neste projeto (código de
  referência `OR_BACR2_44`)**, então essa PR não vai ser mergeada como
  está. Decisão tomada com o João: substituir por um adapter usando o
  **OSRM** (servidor público `router.project-osrm.org`, sem API key — mesmo
  padrão de uso livre já aceito neste projeto para o Nominatim), atrás da
  mesma interface `RouteAdapter` que o Marco já criou na PR #34 (já estava
  desenhada separada do `MapsAdapter` de geocoding de propósito, então não
  precisa mudar — só troca a implementação concreta). Aviso registrado:
  assim como o Nominatim, endereços rurais têm cobertura fraca no OSRM
  também.
  **Classificação:** (a) só front/adapter — Dev 2.
  **Status:** pendente, vai substituir a PR #36 (`feature/ms1-osrm-route-adapter`).
- **Nome do orçamento por padrão em "Data + Especialidade + Propriedade"
  (editável).** O backend já tem um default mais simples
  ("DD/MM/AAAA - Especialidade", sem propriedade — ele não conhece o nome
  da propriedade, ADR-001 sem join cross-service) e o campo já é editável
  pelo usuário. Decisão tomada com o João sobre o formato exato: **
  `DD/MM/AAAA - Especialidade - Propriedade`** (mesmo separador ` - ` que o
  backend já usa, só acrescentando a propriedade no fim). A tela (não o
  backend) é quem monta esse valor mais rico antes de enviar.
  **Classificação:** (a) só front — Dev 2.

### Perguntas que já tinham resposta no próprio contrato (confirmadas, sem mudança necessária)

- **O km calculado pode ser editado à mão no orçamento?** Sim — o campo
  `displacementKm` sempre foi um número editável livremente, o cálculo
  automático só preenche um valor de partida.
- **O valor por km deve ser gravado como snapshot no orçamento, em
  centavos?** Sim, já é assim: `Appointment.displacementRateCents` é uma
  cópia própria do orçamento (não lê o perfil na exibição), documentado no
  próprio `shared-types`: "pra que o orçamento antigo não mude quando ela
  mudar".
